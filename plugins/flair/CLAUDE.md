# CLAUDE.md — led-ticker-flair

One wheel, five plugin namespaces: four sprite-trail families (`nyancat`, `pokeball`, `pacman`, `sailor_moon`) plus `flair` (the wheel's own name, for text effects). Each sprite family lives under `src/led_ticker_flair/<family>/`, registered in `src/led_ticker_flair/<family>/__init__.py` as `forward` / `reverse` / `alternating`. The `flair` namespace registers text effects: four animations (`flair.propeller`, `flair.fisheye`, `flair.blink`, `flair.twinkle`), the text-effect transitions (`flair.spinout`, `flair.fireworks`, `flair.stickers`, `flair.poker`, `flair.lightning`, `flair.fairy.*`, `flair.laser.*`, `flair.accordion.*`, `flair.interlock.*`, `flair.blinds.*`, `flair.snow`), three background effects (`flair.fireworks` — same name as the transition, different registry — plus `flair.twinkle` and `flair.snow`), and one widget (`flair.lottery`).

## Invariants

- **One wheel / five entry points** — `pyproject.toml` declares all five `led_ticker.plugins` entry points (`nyancat`, `pokeball`, `pacman`, `sailor_moon`, `flair`). The entry-point NAME is the plugin namespace; transition type strings are `<namespace>.<variant>`, animation type strings are `<namespace>.<name>`, widget type strings are `<namespace>.<name>`.
- **`flair` namespace naming exception** — unlike the four sprite families, the `flair` namespace is named after the wheel itself, not a sprite character. This is an intentional exception to the namespace-per-sprite-family pattern. It registers text effects — the `flair.propeller`, `flair.fisheye`, `flair.blink` + `flair.twinkle` animations, the text-effect transitions (`flair.spinout` through `flair.blinds.*`, plus `flair.snow`), the `flair.fireworks` / `flair.twinkle` / `flair.snow` backgrounds, and the `flair.lottery` widget — and has no `sprites/` directory.
- **Sprites load via `Path(__file__).parent / "sprites"`** — sprites live beside the family module file (e.g. `src/led_ticker_flair/nyancat/sprites/nyancat.webp`). Moving a family submodule without moving its `sprites/` directory breaks sprite loading. The `flair` submodule has no sprites and is not subject to this invariant.
- **Imports only from `led_ticker.plugin`** — enforced per-family by `tests/test_import_purity.py`.
- **No `from __future__ import annotations`** (PEP 649 / Python 3.14 rule).
- Dep: `led-ticker` only.
- Lint/test from the monorepo root: `make lint` / `uv run pytest plugins/flair`. CI is the root path-filtered matrix.
- **Co-dev against an unreleased core:** the `led-ticker-core>=4.3` floor won't
  resolve against an editable pre-release core (hatch-vcs reports e.g.
  `4.2.2.devN`); install with `uv pip install --no-deps -e plugins/flair` and
  run everything via `uv run --no-sync ...` until core 4.3.0 ships. `flair.lottery`
  bumped the floor to `led-ticker-core>=4.10` for the `RotationSurface.blit(...,
  dx_logical=...)` translation seam (see the blit-geometry bullet below); the
  same co-dev pattern applies until core 4.10.0 ships — during development the
  monorepo's own `pyproject.toml`/`uv.lock` carry an uncommitted, worktree-local
  `[tool.uv.sources]` override pointing `led-ticker-core` at the core seam
  worktree. Never commit that override.

## `flair.lottery` widget invariants (`src/led_ticker_flair/flair/lottery.py`)

- **Choreography: rack-fill, not left-to-right.** The first ball to enter rolls to the RIGHTMOST slot; the next stops one slot short; and so on — a rack fills, no ball ever crosses (rolls through) an already-settled one. Reveal order is therefore right-to-left (the last config word lands first), but word index always equals slot index, so the FINAL display still reads the config's `words` left-to-right unchanged. `roll_order_for_slot(slot_index, n)` is the (self-inverse) mapping between a slot's index and its temporal roll order — `draw()`'s per-tick loop walks slots in REVERSED (rightmost-first) order and feeds `ball_phase` the roll order, not the slot index, as its tick-window argument. `ball_phase` itself is pure per-ball math and stays agnostic to which slot owns which window — only this mapping layer changed. The correctness argument is geometric, not just empirical: because slot stride (`diameter + _GAP_PX`) exceeds the ball diameter, and a rolling ball's `cx` never exceeds its own target slot center, a still-rolling ball's footprint can never reach the footprint of any slot further right (i.e. any already-settled one). Tripwire: `TestRackFillChoreography` in `tests/test_flair_lottery.py`, specifically `test_no_ball_ever_crosses_a_settled_one` (snapshots every settled ball's face region every tick and asserts it's byte-identical while any other ball is still rolling — this is the test that pins the regression the fix addresses; it fails hard under the old left-to-right entry order).
- **Draw return is absolute.** `Lottery.draw(canvas, cursor_pos, ...)` returns `(canvas, cursor_pos + canvas.width)` and adds `cursor_pos` (logical px) to every blit's `dx_logical` (rest surface, settling ball, rolling ball; `RotationSurface.blit` clips at both panel edges). The unscaled skip path paints nothing and returns `(canvas, cursor_pos)`. Core's `ticker` / `one_at_a_time` sections pop a widget only when the returned end is `< 0`, so a `canvas, 0` return wedges the section on its first widget. The border frames the panel, not the card: painted unshifted on every draw whatever the cursor (like core's Message / Clock / Count), so it never blinks in `one_at_a_time` or vanishes during a push transition. Guarded by the scroll-mode tests at the end of `tests/test_flair_lottery.py`, which drive core's real `Ticker` loops.
- **Two-surface design, one repaint+snapshot per settle — NEVER per tick.** Each ball owns its own construct-once `RotationSurface` (built by `_ensure_built`, painted with its face ONE time at its slot position, then `snapshot()`'d) plus one shared `_rest_surface` composite that already-settled balls get folded into. Every tick, `draw()` does exactly two kinds of surface work: (1) a flat angle-0 `_rest_surface.blit(canvas, 0.0, 0.0, dx_logical=cursor_pos, ...)` (translated by the cursor) for all already-settled balls (cheap, O(1) regardless of `n`), and (2) a single rotate+translate `blit()` for the one ball currently rolling. A ball transitions from its own surface to the rest composite via exactly one `paint_face` + `snapshot()` call at the tick it settles — never repainted again after that. This is the same perf contract as `flair.propeller`/`flair.fisheye`: painting (SetPixel-heavy, expensive) happens O(1) times per ball; blitting (cheap) happens every tick. Do not "simplify" this into repainting every ball's face every tick — that reintroduces the O(n) per-tick SetPixel cost the two-surface design exists to avoid.
- **Blit geometry — pivot vs. translation (the core >=4.10 seam).** `RotationSurface.blit(canvas, angle_deg, cx_logical, dx_logical=...)` takes the pivot (`cx_logical`) and the translation (`dx_logical`) as independent parameters. Lottery passes the ball's own painted SLOT center as the pivot — this makes the face spin about ITSELF (tumbling in place) rather than about the panel origin — and `dx_logical = current_cx - slot_cx` as the translation, which slides that spinning face sideways to wherever it currently is along the roll. Verified against core's `rotate.rotate_blit` forward map `dst = R(src - c) + c + t`: pivot and translation are independent terms, so this composes cleanly (a word can spin AND slide in the same blit). This translation parameter (`dx_logical`) did not exist before the Phase-0 core seam (PR #367) — it's why this widget bumped the core floor to `>=4.10`. Don't confuse pivot and translation: swapping them (e.g. pivoting on the current rolling position instead of the slot) makes the ball orbit the panel instead of tumbling in place.
- **Roll timeline reads `_frame_count` directly, NOT `frame_for("roll")`.** `FrameAwareBase._EFFECT_ATTRS` is a fixed, enumerated set of named per-effect counters (`"border"` is a member; `"roll"` is not). Calling `self.frame_for("roll")` on an unlisted name would silently alias `self._frame_count` rather than raising — a footgun-shaped trap for a future refactor that assumes every named string works. `ball_phase(frame, ...)` in `draw()` is deliberately called with `self._frame_count` verbatim. If a future change adds `"roll"` to `_EFFECT_ATTRS` upstream in core, this widget's counter semantics (resets to 0 every visit via `reset_frame`, which is also when the two surfaces get dropped/rebuilt = the re-roll) must stay in lockstep with that reset — don't switch to `frame_for("roll")` without re-verifying the reset timing matches.
- **Unit convention: layout is physical, blit args are logical.** `layout()`, `ball_phase()`, and the widget's `_diameter_px`/`_slot_centers_px`/`_r_px` are all REAL (physical) pixels — the balls paint directly to the real canvas via `paint_hires` (bypassing `ScaledCanvas`'s block expansion), same as hi-res emoji, so their geometry must be computed in the same space the panel itself is measured in. But `RotationSurface.blit()`'s `cx_logical`/`dx_logical` arguments are LOGICAL — the widget's own drawing space, matching `paint_face`'s `cx_logical`/`cy_logical` params. `draw()` converts at the boundary: `cx_logical = cx_real / canvas.scale` before computing `dx_logical = cx_logical - slot_cx`. Getting this backwards (passing a physical-pixel value where `blit` expects logical, or vice versa) produces a ball that rolls at the wrong speed or position without raising — verify unit provenance at every call site that touches both spaces, not just the ones that "look wrong" on inspection.
- **`y_offset` renders the CURRENT roll frame shifted, via `dy_logical` — not an all-settled substitute (fixed; was the MAJOR finding from the lottery review).** `y_offset` is LOGICAL units, the same unit `RotationSurface.blit`'s `dy_logical` keyword takes (core `>=4.10` — see the co-dev note above; `dy_logical` landed as part of the same seam as `dx_logical`), so `draw()` forwards `dy_logical=float(y_offset)` to every `blit()` call (the rest-surface identity blit AND the per-tick rolling/settling blits) instead of branching to a separate direct-paint path. There is no longer a `y_offset != 0` special case: the SAME two-surface rendering runs regardless of `y_offset`, just translated. Consequences (correct, by design): an incoming push transition resets the widget first (frame 0, `RotationSurface`s dropped) — so the push slides in whatever frame 0 actually looks like (empty / a ball barely leaving the left edge), and the roll plays out AFTER the push completes, preserving the reveal. An outgoing mid-roll push shows the exact mid-roll state (some balls settled, one rolling, others off-canvas), shifted — no more unrolled balls popping into existence. This is safe specifically because `run_transition` calls `pause_frame()` around the whole transition, so repeatedly drawing "the current frame" during a multi-tick transition composite is a still frame, not a redraw of an advancing roll. Tripwire: `TestLotteryWidget.test_y_offset_renders_current_frame_shifted` (mid-roll shift-consistency) and `test_y_offset_incoming_push_does_not_reveal_finished_row` (regression probe for the original bug) in `tests/test_flair_lottery.py`.
- **Unfittable-word warn latch (`_warned_words`).** `paint_face` logs one WARNING per unfittable word (a word whose largest font size at the ball's diameter still doesn't fit — `auto_font_size` returns 0). Without a latch, every visit's `_ensure_built` rebuild (which happens on every `reset_frame`, i.e. every re-roll) would re-log the same word forever. `_warned_words` is a `set[str]` that persists ACROSS `reset_frame` calls (deliberately NOT reset alongside `_surfaces`/`_rest_surface`/`_built_for`, which DO get dropped every visit) — it's keyed on the word/font/diameter combination being persistently unfittable, not on a specific surface generation. `_ensure_built` passes `warn=not fits and word not in self._warned_words` per word and adds to the set right after checking; the settle-time `paint_face` call passes `warn_unfittable=False` unconditionally (the one warning already fired during `_ensure_built`, if it was going to).

## `flair.fireworks` transition invariants (`src/led_ticker_flair/flair/fireworks.py`)

- **Two-phase design, painted through black — no compositing from prior frames.** Phase one (`t < 0.5`, `frame_at`) draws the outgoing widget every frame, then overlays staggered burst launch-streaks/open-circles/rim sparks on top. Phase two (`t >= 0.5`) draws the incoming widget every frame, then calls `_blackout_complement` to black out everything OUTSIDE the union of all bursts' current circles. This shape — draw the "real" widget fresh, then paint an effect mask on top, every single frame — exists because of the **no-`GetPixel` constraint** (core constraint #3): the real hardware framebuffer stores pre-computed GPIO bitplane data, not readable RGB, so there is no way to sample "what's on the panel right now" and erase around it incrementally. Every frame is computed from scratch from pure burst geometry (`plan_bursts`/`burst_state`) plus a fresh `widget.draw()` call — never from the previous frame's pixels. Don't "optimize" this into an incremental diff against a remembered previous frame; that path doesn't exist on real hardware.
- **Per-row interval-union complement (`_blackout_complement`).** A circle intersects any given row `y` in AT MOST ONE contiguous x-interval — `half = sqrt(r**2 - (y - cy)**2)` when `|y - cy| <= r`, giving `[cx - half, cx + half]` (clamped to `[0, w)`). For each row, every currently-open burst contributes at most one such interval; `_blackout_complement` collects them, sorts by start, merges overlaps, then `SetPixel`-blacks only the GAPS (before the first merged interval, between merged intervals, after the last) — `O(h * n log n + black_pixels)`, i.e. cost scales with the ACTUAL black area rather than with bounding-box size. This replaced an earlier `bytearray(w*h)` union-mask design (stamp each burst's bounding box, then one full-panel scan): deep in the "bloom" phase every burst's radius grows toward `hypot(w, h)` (see `burst_state`'s `"bloom"` phase), and the mask version's worst case wasn't just "one burst individually covers the whole panel" (which an earlier corner-check short-circuit handled) — several bursts jointly, but not individually, covering the panel still forced the mask version through a full stamp-then-scan on every burst's bounding box even though the final black-pixel count was zero or near-zero (measured ~8ms dev / ~56ms projected Pi-5 at 512x64, mid-bloom — over the ~50ms/20fps budget). The per-row algorithm has no mask to stamp, so that joint-partial-coverage case is now cheap too: a row whose merged interval already spans the whole panel yields zero gap pixels out of the SAME per-row loop every other row goes through, at the same `O(n log n)` cost — full coverage falls out of the general case for free, no special-cased short-circuit needed. Measured worst frame across a full bloom-phase sweep (`t` in `[0.5, 1.0)`), multiple burst counts/seeds, at 512x64: ~0.2–0.5ms dev (was ~8–10ms with the mask version). Tripwires: `TestLateBloomPerfShortCircuit` in `tests/test_flair_fireworks.py` (zero black `SetPixel` calls when a burst's radius covers the panel — same assertion, now satisfied by the general per-row case rather than a dedicated branch) and `test_mid_bloom_paints_far_fewer_than_half_the_panel` (the specific joint-partial-coverage regime that used to be the mask version's worst frame — bounds the complement paint count well under a half-panel's worth of pixels).
- **Explicit `seed` reproducibility is per-instance-per-firing, not "forever."** Two FRESH `Fireworks` instances constructed with the same explicit `seed` plan an identical FIRST firing (the underlying `random.Random(seed)` starts from the same state). But firing the SAME instance a second time (`frame_at` detects a new sweep via `t < self._last_t`, the Spinout re-fire idiom) does NOT reseed when `seed` was explicitly given — it continues drawing from that same rng stream, so the second firing's plan differs from the first even though the seed never changed. Only the `seed=None` (default) path reseeds `self._rng` from fresh OS entropy on every re-fire; an explicit seed exempts the *reseed*, not the *replan* — a stale `_plan` is still dropped and rebuilt on every re-fire regardless of whether `seed` is set (see `test_refire_with_explicit_seed_still_rebuilds_a_plan`). Tripwire: `TestSeedRefireSemantics` in `tests/test_flair_fireworks.py` (same instance/seed → two firings' plans differ; two fresh instances/same seed → first firings identical).
- **`transition_colors` does NOT reach plugin transitions.** Core's `[transitions]`/section-level `transition_colors` config key is a core-transition-only knob (a known gap, not a Fireworks-specific limitation) — `Fireworks.__init__`'s own `colors` constructor kwarg (validated: non-empty list of `[r, g, b]` int triples 0-255) is the ONLY way to override the burst palette from TOML, via the dict transition form: `transition = {type = "flair.fireworks", colors = [[255, 60, 60], [0, 220, 220]]}`. Don't add a `transition_colors` read path to this module expecting it to be wired by core — it isn't.
- **All burst geometry paints at physical resolution, bypassing `ScaledCanvas`.** Same hi-res-paint design as `flair.lottery`'s ball faces and inline hi-res emoji: `frame_at` calls `unwrap_to_real(canvas)` once per tick and every burst-drawing helper (`_draw_launch_streak`, `_fill_burst_black`, `_draw_spokes`, `_blackout_complement`) takes that `real` canvas and calls `real.SetPixel` directly — never `canvas.SetPixel` — so on a scaled (bigsign/longboi) display a burst renders at full panel grain rather than a blocky `scale x scale`-block approximation. Tripwire: `TestScaledCanvasEffectPixels` in `tests/test_flair_fireworks.py`.
- **Snap idiom matches `spinout`/`fisheye`.** `frame_at` calls `snap_reset(canvas, kwargs.get("incoming_bg_color"))` then `incoming.draw(canvas, cursor_pos=0)` at `t >= SNAP_THRESHOLD` (0.95) — `run_transition` does NOT snap on this transition's behalf. `min_frames = 24` (spec-recommended) raises the runner's frame floor so the two-phase launch/bloom choreography isn't compressed into too few ticks at a short `[transitions] duration`.
- **Asterisk-burst decoration: radial spoke trails, not a ring (PR #39 rework, 2026-07).** An earlier "visual-punch fix" pass (2026-07) replaced sparse dim spark points with a continuous bright ring outline (`_draw_ring`) plus 2x2 spark blocks (`_draw_sparks`) — that shipped, but James's PR #39 review called it out as reading like a RIPPLE, not an explosion (a continuous circle outline just isn't what a firework burst looks like). `_draw_ring`/`_draw_sparks`/their brightness helper `_ease_brightness` are gone entirely; `_draw_spokes` is the sole decoration painter now. Per burst: one radial trail per seeded `Burst.spoke_angles` entry (10-14 spokes, narrowed from the old 16-32 spark count so individual trails read distinctly instead of blurring into a haze), each a line of pixels from a tail near the center out to a head riding `_SPOKE_HEAD_OFFSET_MIN.._MAX` (1-2px) ahead of the current hole radius. `trail_len = _TRAIL_LEN_FRAC (0.45) * r_head * variance` (`variance` in `[0.85, 1.15]`, seeded) — since trail length scales with the hole's own radius, early bursts are short dense stars and late (bloomed) bursts have long trails, with no extra time-keyed easing needed for that shape. Brightness is a per-pixel gradient along the spoke: the outermost `_SPOKE_WHITE_HOT_PX` (1.5) px render pure white regardless of burst color (the "hot particle head" read), the rest fades linearly in the burst's own color from full brightness down to `_TAIL_BRIGHTNESS_FLOOR` (25%) at the tail. `_bloom_multiplier(t)` scales the WHOLE spoke, head included, on top of that gradient during the bloom phase (see the next bullet for its CURRENT — post-tail-fix — curve; it no longer floors at 25%). Both the head-offset and the trail-length variance are derived from each spoke's own already-seeded `jitter_deg` (same "no fresh rng draw" trick the old spark radius jitter used), so the whole decoration stays a pure function of the committed plan. Iteration is radial (angle computed once per spoke via `cos`/`sin`, then the radius stepped by 1px) — cost is `O(spokes * trail_len)` per burst, comparable to or cheaper than the old ring's arc-length stepping. Launch-streak geometry (`_draw_launch_streak`, `_LAUNCH_HEAD_LEN`/`_LAUNCH_TAIL_LEN`, the 0.35 `_LAUNCH_OPEN_BOUNDARY`) is unchanged — it read fine, per PR #39 feedback. None of this touches hole/complement mechanics (`_fill_burst_black`, `_blackout_complement`, `burst_state`'s radius formulas) — purely the decorative layer painted on top. Tripwires: `TestDrawSpokes` in `tests/test_flair_fireworks.py` (spoke-angle pixel placement, white-hot head, tail-dimmer-than-head, bloom fade scales the whole spoke).
- **Decoration is DECOUPLED from the hole reveal during bloom — coast + fade-to-zero before the snap (tail-fix, PR #39 v3 review, 2026-07).** The asterisk rework above (v2) fixed the ring-vs-explosion read but introduced a new problem: `_draw_spokes`'s `radius` argument was `burst_state`'s own hole radius, which grows LINEARLY toward `hypot(w, h)` across the whole bloom half (~10x `radius_max` by `t == 1.0`, by design — that's what guarantees full-panel coverage). Chaining the DECORATION to that same radius made the spokes themselves accelerate off-panel at high speed, then get deleted outright by the `SNAP_THRESHOLD` (0.95) cut — James's v3 feedback: a visible "fly-off-then-cut". The hole/complement formulas that growth curve drives are correct and untouched by this fix; only the decorative layer's OWN radius/brightness needed to stop tracking it, via two independent knobs: **(1) position** — `_spoke_bloom_radius(radius_max, t)` replaces the hole radius as `_draw_spokes`'s `radius` argument once bloom starts (`frame_at`'s bloom branch): heads ease out from `radius_max` (continuous with the "open" phase's own final radius at `t == _BLOOM_AT`) via `radius_max * (1 + _SPOKE_COAST_GROWTH * (1 - (1 - q) ** 2))` where `q = min(1, (t - _BLOOM_AT) / _SPOKE_COAST_WINDOW)` — i.e. coast `_SPOKE_COAST_GROWTH` (35%) farther over `t` in `[0.5, 0.75]`, then HOLD that final radius flat for the rest of the transition (`q` clamps at 1.0 past the coast window, so this is a plateau, not a continuation of the curve). **(2) brightness** — `_bloom_multiplier(t)` no longer floors at `max(0.25, ...)`; it now holds full brightness through `_SPOKE_FADE_START` (0.6) and fades LINEARLY to EXACTLY `0.0` by `_SPOKE_FADE_END` (0.85), staying at 0 afterward — `frame_at`'s bloom branch skips the whole per-burst `_draw_spokes` loop once this returns 0 (nothing to paint). Reaching zero well before `SNAP_THRESHOLD` means the final ~0.1 of the transition, pre-snap, shows ONLY the incoming widget finishing its own bloom — the snap then changes nothing visible, closing the "abrupt cut" half of the bug. Both curves are independent of the hole radius and of each other; `_fill_burst_black`/`_blackout_complement`/`burst_state` are unmodified by this fix. Tripwires: `TestBloomMultiplier` (fade curve: full through 0.6, zero at/past 0.85), `TestSpokeBloomRadius` (position: matches `radius_max` at bloom start, coasts through the window, holds flat after — including a pixel-position check via `_draw_spokes` directly, bypassing the brightness gate, that t=0.9 lands at the same distance from center as the t=0.75 plateau), `TestNoDecorationBeforeSnap` (integration via `frame_at`: only the incoming widget's fill color and/or complement-blackout black may appear at t in `{0.86, 0.9, 0.94}` — no white-hot or burst-colored spoke pixels) in `tests/test_flair_fireworks.py`.

## `flair.fireworks` BACKGROUND invariants (`src/led_ticker_flair/flair/fireworks_background.py`)

- **Same name, different registry — and it is a `background`, NOT a `border`.** `api.background("fireworks")(FireworksBackground)` sits beside `api.transition("fireworks")(Fireworks)`; core's `_coerce_background` resolves `"flair.fireworks"` in `_BACKGROUND_REGISTRY`, transitions in theirs. It shipped for one unreleased commit as `api.border` (plugins#128); that spent the host's only `border` slot, so core grew the dedicated `background` layer (core >= 4.32, painted background → image → border → text). Never re-register it as a border. Tests' per-file `_RecordingAPI` fakes MUST expose `background()` (they all do) or `register()` raises mid-way and every registration test in the file fails.
- **Pure function of `(frame_count, real dims)` per instance — never a stateful sim.** Transitions pause the host's frame counter and re-render the widget repeatedly at the SAME frame while compositing; a particle sim that advanced per `paint()` call would smear. Slot plans come from `random.Random(_slot_seed(slot, epoch))` (seed mixed with slot in bits 48+ and `epoch = floor(frame/cycle + slot/n)` in the low bits), phase is arithmetic on `frame_count`. `seed=None` draws ONE instance seed at construction and is frame-pure thereafter. Tripwires: `test_pure_function_of_frame`, `test_unseeded_instance_is_still_frame_pure`, `test_rng_seed_mixing_differs_per_slot_and_epoch`.
- **Never paints black.** It reuses `Fireworks._draw_launch_streak` / `Fireworks._draw_spokes` (pure painters) but NOT `_fill_burst_black` / `_blackout_complement`; the `_LightOnly` SetPixel proxy drops `(0,0,0)` writes that the spoke tail/fade math can round to. A background stamping black would erase a host's `bg_color` / image. Tripwire: `test_does_not_black_out_pixels`.
- **`frame_invariant = False`, `restart_on_visit = False`** — the first so `gif`/`image` static fast paths don't freeze it (core's `BackgroundEffectBase.__init_subclass__` refuses a subclass that omits the attribute), the second so the show runs continuously across `loop_count > 1`.
- **Physical resolution, real dims.** Paints to `unwrap_to_real(canvas)`; `burst_count` / radius use the REAL panel dims, not the logical wrapper. Tripwires: `TestScaledCanvas` (patches `ScaledCanvas.SetPixel` at the class to fail on any wrapper write — the wrapper is attrs-slotted, so instance patching is impossible).
- **`speed` scales the cycle exactly.** `cycle = max(8, round(CYCLE_FRAMES / speed))`; phase is `frame/cycle + slot/n` (fractional stagger, not an integer offset) so `speed=2` at frame `k` reproduces `speed=1` at frame `2k` bit-for-bit. Tripwire: `test_speed_scales_cycle_length`.

## `flair.stickers` transition invariants (`src/led_ticker_flair/flair/stickers.py`)

- **Plan-time rasterization only; never rotate or capture per frame.** Stickers are captured (`capture_sprite`), composed with black backing + white rim (`compose_sticker`), and rotated to their assigned angle (`rotate_pixels`) ONCE during the first `_ensure_plan` call for a given canvas size/scale — the result is cached in `StickerRaster` keyed by `(slug, angle_deg, scale, content_height, footprint)`. `frame_at` paints these pre-rasterized pixel dicts directly on every tick without regeneration; the per-frame loop only computes arrival/departure indices and blits the cached result. A per-frame rasterization or rotate path would blow the 50ms budget on the first frame after a plan (every arriving sticker is a fresh, uncached combo). Tripwire: `TestPerf.test_no_rasterization_after_first_frame` in `tests/test_flair_stickers.py` (raster cache hit rate must be ~100% after the first tick following plan build).
- **Coverage at `t=0.5` is guaranteed by jittered-grid + square-card-backing construction (default `backing = "card"` ONLY — `"shadow"`/`"none"` deliberately forfeit it for the swarm look; `TestBackingKnob::test_none_backing_leaves_gaps_at_half` pins the tradeoff).** `plan_stickers` lays out a jittered grid (random position jitter within each cell, random angle per sticker, randomized arrival/departure order) with `cell = max(1, int(footprint * GRID_OVERLAP))` where `GRID_OVERLAP = 0.7` — this ensures no gaps when adjacent grid cells' square cards overlap. `compose_sticker(sprite, footprint=<int>)` backs each sticker with a solid square of side `footprint`, centered on the sprite's bbox center (NOT a silhouette-shaped backing), so the composed sticker matches the geometric footprint model exactly. Coverage is verified across all drawable emoji and both panel geometries (smallsign + bigsign) via `TestEndpoints.test_full_cover_at_half` and the plan module's seed-sweep calibration tests (`test_flair_stickers_plan.py::TestCoverage`). If coverage ever fails (e.g. a new emoji breaks the inscribed-square model), tighten `GRID_OVERLAP`; do not weaken the tests.
- **Knob validation resolves through core's `emoji_slugs()`; never inline a slug list.** `Stickers.__init__` validates the `emoji` param via `set(emoji) - set(emoji_slugs())` to catch unknown slugs at config-load time; `led-ticker validate` then raises with the list of offenders. Never hardcode a known-slugs check that duplicates the upstream `emoji_slugs()` registry — that list changes when plugins register new emoji and our validation must stay in sync. Tripwire: `test_unknown_emoji_raises_at_config_load` in `tests/test_flair_stickers.py`.
- **`frame_at` recomputes `unwrap_to_real(canvas)` EVERY call; never cache the real canvas across frames.** The canvas object handed to `frame_at` on any given tick is very likely a DIFFERENT back-buffer than the previous tick (constraint #1 — `frame.swap()` returns a different canvas each call). `_ensure_plan` re-derives `real = unwrap_to_real(canvas)` on every call (cheap attribute lookups) so the per-frame loop (`frame_at`'s second half) always paints into the current tick's real back-buffer, never into a stale canvas from a prior swap. A single-call cache keyed only on dims would silently keep painting onto an old buffer on every tick after the first, freezing the panel when the old front-buffer re-enters the swap queue. Tripwire: the conformance suite's `run_backend_conformance` already catches dropped-capture patterns via the stub's double-buffer rotation (`SwapOnVSync` returns a different canvas each call); a stale-canvas bug surfaces immediately when run with the test stub.

## `flair.poker` transition invariants (`src/led_ticker_flair/flair/poker.py`)

- **Suit shapes are pure-math masks, used for resting glyphs and every ripple ring.** The four suits (heart, diamond, club, spade) are defined via `inside(suit, dx, dy, r)` implicit-curve or lobe-based point-in-polygon functions. Ring pixel-lists (the ripple wavefronts) are computed as `interior_pixels(r) - interior_pixels(r - RING_W)` once per firing via `RingCache`; both glyph interiors and ring shells are keyed by `(suit, radius_int, hue_deg)` and never rasterized twice. The key insight is that the REVEAL mask — the union of every ring swept so far — is ACCUMULATED (not delta-computed) because the suits are NOT radially monotone (a point above a club's center is inside a small club's top lobe but OUTSIDE a large one as the lobes scale outward) — accumulation is what guarantees gap-free full coverage by `SNAP_THRESHOLD` even if no frame samples the outermost radius. Full reveal is pinned by `test_full_reveal_clubs_regression` (known-bad seeds on bigsign + smallsign) and the `_MAX_R_FACTOR = 1.45` safety margin: if a suit ever regresses to leave unrevealed pixels, RAISE the factor, never weaken the test. Tripwire: `TestPerf.test_no_ring_rasterization_after_first_frame` (spy/mutation check that ring cache is never re-keyed after the first frame — cost must be O(1) per tick, not O(rings)) in `tests/test_flair_poker.py`.
- **`frame_at` recomputes `unwrap_to_real(canvas)` EVERY call; never cache the real canvas.** Same logic as the stickers invariant: the canvas handed to `frame_at` on any tick is very likely a different back-buffer than the previous one (`frame.swap()` returns different canvases each call). `_ensure_plan` re-derives `real = unwrap_to_real(canvas)` on every call (cheap attribute lookups); every subsequent frame paints into the current tick's real back-buffer, never a stale one. A cache keyed only on dims would keep painting onto old front-buffers when they cycle back into the swap queue, freezing the panel. The conformance suite's double-buffer rotation catches this immediately via the test stub's `SwapOnVSync` returning a different canvas each call.
- **Snap idiom, incoming_bg_color forwarding.** `frame_at` calls `snap_reset(canvas, kwargs.get("incoming_bg_color"))` then `incoming.draw(canvas, cursor_pos=0)` at `t >= SNAP_THRESHOLD` (0.95) — `run_transition` does NOT snap on this transition's behalf. The two-phase structure (outgoing + ripples, then incoming + black complement + ripples) means the snap's purpose is to anchor the incoming widget's own background color the instant the final frame renders, preventing the "border on black" flash. See the stickers snap idiom above for the full context.


## `flair.laser` transition invariants (`src/led_ticker_flair/flair/laser.py`)

- **Snapshot-only erase — the outgoing is NEVER drawn live after the snapshot.** `frame_at` draws each widget ONCE per firing into a plugin-local readable `_Raster` (through a `ScaledCanvas` wrapper when the live canvas is scaled, so hires widgets paint exactly as on the panel) and every subsequent frame paints from the resulting pixel lists. A live `outgoing.draw` per frame can drift from the snapshot over a ≥2.4 s transition (a clock's seconds, a source refresh) and leave pixels no beam ever erases, which then vanish abruptly at the phase boundary. Refire detection is `t < _last_t` (spinout/fairy idiom); equal `t` is not a refire. Tripwires: `test_outgoing_not_drawn_live_after_snapshot`, `test_refire_resnapshots_changed_incoming`, `test_equal_t_is_not_a_refire` (`tests/test_flair_laser_transition.py`).
- **Lit = slot set AND not pure black; the section `bg_color` never enters a snapshot.** The engine (`reset_canvas` / `run_transition`'s per-frame `Fill`) paints the section bg, never the widget, so the raster holds only widget content and the erase phase needs no outgoing-bg knowledge: an erased pixel simply stops being painted and the runner's `Fill(outgoing_bg)` shows through. Black is excluded so gif pillars / image letterbox fills aren't lasered. Widget-LEVEL fills (image `bg_color`, two_row bands) are content and get lasered. No `outgoing_bg_color` kwarg exists or is needed — don't add a core seam for it. Tripwire: `test_black_and_unset_are_unlit` (`tests/test_flair_laser_plan.py`).
- **`_Raster.SetImage` must exist.** `gif` / `image` / `still` widgets paint via `unwrap_to_real(canvas).SetImage(pil, x, y)`; a snapshot target without it raises inside the breaker-guarded draw and TRIPS the widget (disables it for the session), not just the snapshot. It decodes the PIL image into slots (alpha 0 → black, mirroring core's `HeadlessCanvas`). Tripwires: `test_setimage_alpha_zero_is_unlit_and_clips`, `test_image_widget_snapshots_through_setimage`.
- **Constant pixel speed per beam; everything visited at `SNAP_THRESHOLD`.** For an `n`-pixel track `visited(t) = n if t >= 0.95 else int(n * t / 0.95)`; the first `n_out` visits erase, the rest write, so erase/write time splits in proportion to the lit counts (empty outgoing → straight to writing). `min_frames = 48` floors the runner at 2.4 s. Tripwires: `test_all_incoming_visited_at_0_95`, `test_empty_outgoing_starts_writing_immediately`.
- **Raster order is physical lines, boustrophedon, origin edge first, parity carried into the write phase.** Lines are REAL rows (top/bottom) or columns (left/right); the first line is nearest the origin edge; direction flips only after a line that contributed ≥ 1 pixel (empty lines cost no frames); `raster_order` returns the parity the write phase starts with, so one beam rasters continuously across the erase/write boundary. Tripwires: `TestLaserFrames` + the `raster_order` tests in `test_flair_laser_plan.py`.
- **`beams` (default 3) splits the lit CONTENT extent, not the panel.** `_spans` takes the union of the outgoing and incoming lit extents along the across axis and cuts it into `beams` near-equal slices (clamped to the extent width); each slice is an independent (erase, write) track with its own head and speed. Splitting the panel width instead hands a centred headline to a single beam (the first spike did this — all three beams but one were empty). Two rasters are kept alive at once so both extents exist when spans are computed. The bg cuts over (`snap_reset(canvas, incoming_bg_color)` per frame) the moment ANY beam starts writing. `LaserAlternating` / `LaserRandom` forward `beams` to their four sub-transitions. James dropped an every-line-at-once mode after the spike gifs ("a blur unrelated to the final letters") — don't resurrect it as a knob value. Tripwires: `TestBeams`.
- **`write_from` is a second origin for the WRITE phase only.** The type's `_origin` is the erase edge; `_write_origin` resolves `write_from` (`None` → same edge, `"opposite"` → `_OPPOSITE[_origin]`, else the named edge) and every write-phase head draws its beam from THAT edge while erase-phase heads keep the erase edge (`_draw_beam` takes the origin per head). Same-axis pairs share `_spans` over both rasters so a beam erases and writes the same slice and raster parity carries over; cross-axis pairs split each raster's extent on its own axis and pair tracks by index (an unmatched beam gets an empty side — the existing empty-list paths handle it). The multi variants forward `write_from` unchanged; `"opposite"` therefore flips per sub-transition. Tripwires: `TestWriteFrom`.
- **Physical resolution, one-real-pixel beam, `unwrap_to_real` every call.** All painting is `real.SetPixel` on `unwrap_to_real(canvas)` re-derived per frame (constraint #1 — never cache `real`); the `_Raster`s and their geometry key ARE reusable across frames and firings. On the bigsign a logical pixel is written as four passes of four real pixels; the beam spans from the REAL panel edge (through any letterbox band) to the head. Tripwires: `test_scaled_canvas_beam_is_one_real_pixel_wide`, `test_beam_reaches_real_edge_through_letterbox_band`.
- **Snap idiom + `scale_switch_at = 1.0`.** At `t >= SNAP_THRESHOLD`: `snap_reset(canvas, incoming_bg_color)` then `incoming.draw(canvas, cursor_pos=0)` — the runner does not snap on the transition's behalf. Hard-edged family convention keeps the outgoing-scale wrapper for the whole transition; a cross-scale incoming pops to size on the snap frame (same accepted limitation as fairy/lightning/fireworks).
- **Perf bound.** Per frame: at most `n_out` (unvisited, erase) or `n_in` (visited, write) SetPixels per track plus one beam per track — bounded by panel px + beams × panel dimension; the one-time snapshot frame (two widget draws + a raster scan) is the only non-trivial cost. Tripwires: `TestPerfUniformity` (text, alternating refire, full-panel fill on bigsign dims).

## `flair.accordion` transition invariants (`src/led_ticker_flair/flair/accordion*.py`)

- **Column-owner occlusion; no bg-colour knowledge, no core seam.** `accordion_compose.compose` gives each real column to the topmost card covering it and paints only that card's lit pixels, so the section background shows through everywhere else and nothing ever needs the outgoing/incoming bg colour. Do not add a core seam for it. Tripwires: `test_top_card_occludes`, `test_unlit_top_cells_paint_nothing`, `test_no_buried_card_overpaint` (`tests/test_flair_accordion_plan.py`, `tests/test_flair_accordion_transition.py`).
- **Continuity rule and endpoint anchors.** Motion (`accordion_motion.py`) is pure math from phase progress `k` to per-card x. Positions are continuous in `k`, and the endpoints are anchored: outgoing `k=0` equals the slots, outgoing `k=1` is fully off-screen, incoming `k=0` is off-screen, incoming `k=1` equals the slots. Never break continuity with a clamp that jumps. Tripwires: `test_continuity`, `test_out_k0_is_slots`, `test_out_k1_offscreen`, `test_in_k0_offscreen`, `test_in_k1_is_slots`, `test_end_of_incoming_phase_equals_slots`, `test_t0_positions_equal_slots_clipped_content`.
- **Adaptive peek `P_eff`.** Each deck's peek is `min(2*scale, avg slot spacing)` (`effective_peek`) so a dense deck never overlaps more than it spaces, and a stacked deck is never wider than the fanned one. Tripwires: `test_effective_peek_caps_to_avg_spacing`, `test_stacked_never_wider_than_fanned`, `test_scaled_peek_is_8_real_px`.
- **Lazy incoming snapshot + default `scale_switch_at`.** Unlike laser, accordion keeps the runner's default `scale_switch_at` (0.5) and snapshots the incoming widget on the first `t >= 0.5` frame from that frame's (possibly re-wrapped) canvas, so a cross-scale incoming gets its native size for the whole incoming phase. Eager incoming snapshots are a bug. Timeline: outgoing `[0, 0.475)`, beat `[0.475, 0.5)`, incoming `[0.5, SNAP_THRESHOLD)`, then snap. Tripwires: `test_keeps_runner_default_scale_switch`, `test_incoming_not_drawn_before_half`, `test_cross_scale_incoming_snapshot_uses_new_wrapper`, `test_geometry_change_reallocates`, `test_beat_paints_nothing`.
- **Border ring is static and painted AFTER the cards; the ring is what the border paints ALONE.** `_Accordion._border_only` repaints the widget's border by itself (`border.paint(wrapper, widget.frame_for("border"))`, same wrapper as the snapshot) and `exact_ring` keeps as ring only the snapshot pixels that equal that render; every other lit pixel, including text overlapping the ring zone, is content and goes to the cards (segmented over the full panel). Border pixels the content covered go to `Plan.under`, painted BEFORE the cards, so the ring has no hole once a card leaves. Never freeze ring-zone pixels by depth alone when a border-only render is available: left-aligned or right-flush text leaves glyph slivers stuck at the edge. When the render is impossible or untrusted (no `paint` / non-int `frame_for`, a raise, nothing lit, or < 50% colour-exact match, `_RING_MATCH_MIN`), `build_decks` falls back to the depth-based ring below. Tripwires: `TestRingZoneContent` (`tests/test_flair_accordion_transition.py`), `test_exact_ring_splits_content_from_border`, `test_exact_ring_untrusted_render_falls_back`, `test_border_ring_static_and_on_top`, `test_right_border_two_row_combined`, `test_ring_pixels_in_real_coords`, `test_bordered_inset_splits`.
- **Ring depth resolution order (`ring_depth`, the FALLBACK ring; runs only when `widget.border is not None` and no trusted border-only render exists).** (1) an int `thickness` (the core ring borders: rainbow / color_cycle / constant / bands); (2) **`LightbulbBorder`**, duck-typed on an int `gap` plus a callable `_resolve_bulb_size(real_height)`: depth = the bulb size, delegated to the border's own resolver so core's auto rule (1 on panels < 32 tall, 3 otherwise) lives in ONE place. Every bulb is an N x N square flush with the edge, so N is exact on every geometry and in every mode, including `unlit_color = (0, 0, 0)` where a chase ring is too sparse to measure; (3) unknown shapes: the measured four-edge fallback (`_measured_depth`) — layer `d` is ring only if its top row, bottom row, left column AND right column are each >= 20% lit (`_RING_EDGE_COVERAGE`). 20% admits sparse 1x1 bulbs at gap 3 (~25%); the all-four-edges rule is what stops text or an image touching one or two edges from reading as a ring. Never go back to the old "top rows >= 50% lit" heuristic: it gave depth 0 for the default lightbulb on 160x16 and 128x64, so the bulbs became cards and slid away. The `_resolve_bulb_size` probe is a private core method reached by duck-typing (no import); if core renames it, step (3) still measures default-coloured bulbs correctly on all three reference geometries, and only the black-unlit case regresses. Known limit: an unknown-shape border over a full-bleed image measures up to the `h // 4` cap. Tripwires: `test_core_border_ring_depth`, `test_core_border_no_inset_card_touches_ring`, `test_lightbulb_measured_fallback_without_duck_type`, `test_ring_depth_ignores_content_touching_top_edge`, `test_ring_depth_ignores_full_height_text` (`tests/test_flair_accordion_plan.py`), `test_lightbulb_ring_static_smallsign` (`tests/test_flair_accordion_transition.py`).
- **Image/gif widgets: no ring, one band.** Core image widgets' `draw()` (the transition path) paints only the picture, never the border or text overlay, so `is_image_widget` (duck-typed: async `play` + `_paint_full`; works through the transition draw guard) gives them ring depth 0 and a single band even with a `border` or `bottom_text`. Tripwire: `TestImageWidget::test_bordered_two_row_image_slides_as_one_deck`.
- **Per-band decks for two_row, one shared trajectory.** Two-row content is split at the band boundary into separate decks that move in lockstep: the `*_decks` motion functions derive ONE anchor (stretch) / hand (sweep) trajectory from the union of every deck's extents, and each deck keeps only its own slots and peek. Never position a deck from its own extents alone: rows of different widths then shear apart mid-phase even though they meet at k=0 and k=1. Tripwires: `test_two_row_decks_in_sync`, `test_two_row_decks_lockstep_mid_phase`, `test_two_row_bands_split_at_boundary`, `test_two_row_bands_scaled`.
- **Snapshot-only.** The outgoing is never drawn live after its snapshot (`test_outgoing_not_drawn_live_after_snapshot`); refire is `t == 0.0 or t < _last_t` — t=0 always starts a firing so one cancelled after its t=0 frame can't leak its plan into the next; equal non-zero t is a repeated frame (`test_refire_resnapshots`, `test_t0_always_refires`, `test_equal_nonzero_t_is_not_a_refire`); per-frame paint volume is bounded (`TestPerfUniformity`).
- **Background widget = ONE band, ONE card; the two-row split is by row ownership.** `build_decks` gives a widget with a `background` (even a `two_row`) a single band over the whole content area merged by `merge_cards` into one card, so sweep/stretch move it rigidly; per-row decks would have different slots and shear along the row boundary. Otherwise `band_rows` gives the NOMINAL boundary and `split_rows` puts each content pixel (ring excluded) in the deck of the row that draws it: `_Accordion._solo_rows` snapshots two `attrs.evolve` copies of the widget (unwrapping the core transition draw guard via its `_widget` slot), one with `bottom_text = " "` and one with `top_text = " "`, border and band fills dropped, the live widget's `FrameAwareBase` state copied and tokens resolved once (`resolve_tokens_now`); a pixel lit in both solo renders (overlapping rows) or neither goes to the nominal band by position. The live widget is never mutated. No attrs `top_text`/`bottom_text` init fields, or any raise -> `None` -> the plain nominal split; never reintroduce component/majority/dot heuristics as a fallback (the old `assign_bands` still mis-assigned touching rows and was too heavy). Each band's cards come from its own pixels (`cards_from_pixels`). Tripwires: `test_background_widget_is_one_card_per_band`, `test_background_two_row_is_one_card_rigid_under_sweep`, `test_two_row_nudged_glyph_stays_in_one_deck_smallsign`, `test_two_row_descender_crossing_stays_in_one_deck_bigsign`, `test_two_row_dots_stay_with_their_row`, `test_two_row_colon_and_bang_dots_stay_with_their_row`, `test_two_row_crossing_glyph_stays_whole_with_border` (ring exclusion), `test_two_row_overlapping_rows_split_by_owner`, `test_planning_leaves_the_live_widget_untouched`, `test_solo_rows_unwraps_the_transition_guard`, `test_solo_rows_falls_back_for_non_attrs_or_raising_widgets`, the `test_split_rows_*` unit tests (`tests/test_flair_accordion_plan.py`).
- **`.alternating` = two delegated instances, same refire rule.** `_AccordionAlternating` holds one `direction="left"` and one `direction="right"` instance of its motion class and flips `_index` on a new firing, detected with EXACTLY `_Accordion.frame_at`'s rule (`t == 0.0 or t < _last_t`); if the two rules drift, the wrapper flips mid-firing or replays a side. Each inner instance keeps its own plans and rasters. `direction` (validated like `_Accordion`) only rotates the instance list so the first firing uses that side; the left/right instances themselves are unchanged. No `.random`: with two sides, never-repeat random IS alternating. Tripwires: `TestAlternating` (`tests/test_flair_accordion_transition.py`).
- **Shared `_raster.py`.** `Raster`, `Pixel`, `snapshot_into` and `is_lit` live in `flair/_raster.py` and are used by BOTH laser and accordion. Change them with both suites in mind.

## `flair.interlock` transition invariants (`src/led_ticker_flair/flair/interlock.py`)

- **Split, then mesh, split at `t = 0.5`, with the runner's default `scale_switch_at`.** The outgoing strands slide off for `t < 0.5`. The incoming is snapshotted LAZILY on the first `t >= 0.5` frame, from that frame's (possibly re-wrapped) canvas, so a cross-scale incoming meshes in at its native size. Do NOT set `scale_switch_at`. Tripwires: `test_incoming_snapshot_is_lazy_from_rewrapped_canvas`, `test_keeps_default_scale_switch_at`.
- **Content-sized travel, per parity group.** Each parity's shift is `clear_distance` of that parity's OWN lit extent: `size - lo` toward the positive edge, `hi + 1` toward the negative one. The outgoing has just cleared at `t = 0.5` and the incoming appears right after, so the cut-over is the ONLY empty frame. A whole-snapshot extent would let one parity clear early. Panel-size travel left centred text blank for about a third of the transition, and James rejected it. Tripwires: `test_only_t_half_is_empty_for_centred_content`, `test_clear_distance_edge_hugging`.
- **Conveyor direction.** Each parity keeps ONE travel direction across both phases. For `.horizontal`, even strands exit right and enter from the left, and odd strands mirror that. The `*Flipped` classes (used only by `.random`) swap parities. Tripwires: `test_split_moves_even_right_odd_left`, `test_mesh_conveyor_even_enters_from_left_odd_from_right`.
- **Strands are LOGICAL rows anchored at `y_offset_real`.** A strand is `strand * scale` real px, so the bigsign meshes along its 4-real-row pixel grid. Letterbox rows clamp into the first/last strand. Vertical strands anchor at x = 0. Tripwires: `test_strands_anchor_at_y_offset_real_and_clamp_letterbox`, `test_strand_two_meshes_pairs_of_rows`.
- **Snapshot-only, physical resolution, snap idiom.** Neither widget is drawn live after its snapshot. Painting is `SetPixel` on `unwrap_to_real(canvas)`, re-derived every call, and pixels shifted off-panel are skipped. At `t >= 0.95`: `snap_reset(canvas, incoming_bg_color)` + `incoming.draw`. Tripwires: `test_outgoing_not_drawn_live_after_snapshot`, `TestRealCoreWidgets`, `TestPerfUniformity`.

## `flair.blinds` transition invariants (`src/led_ticker_flair/flair/blinds.py`)

- **`scale_switch_at = 1.0`, both snapshots up front.** Old and new share the panel throughout, so the runner's outgoing-bg Fill covers the frame. Each slat's revealed band gets ONE `SubFill` with `incoming_bg_color` (black when `None`), then the revealed incoming pixels, then the unrevealed outgoing pixels. Tripwires: `test_revealed_band_gets_incoming_bg`, `test_revealed_band_black_when_incoming_bg_none`, `test_scale_switch_at_is_1`.
- **Slats are whole logical pixels, over the CONTENT band.** `slat_bounds` gives each slat `(size // scale // n) * scale` real px, the last slat takes the remainder, and the count is clamped so every slat is ≥ 1 logical pixel. Horizontal slats split `content_h_real` anchored at `y_offset_real`, the same anchor as interlock's strands, and `BlindsPlan.bounds` covers ONLY the content band (`extent` is the panel span). A letterbox strip rides its edge slat: it takes the nearest content row's (slat, depth) tag, and `_paint` extends the edge slat's SubFill to the panel edge when the opened run touches that edge — so the leading strip opens with the slat's first row and the trailing strip with its last. Never fold the strips INTO the edge slats' bounds: `revealed` scales by slat size, so the edge slats then open late and fast while a bg band creeps through the letterbox. With a panel-height split instead, a letterboxed sign such as 128×64 at scale 2 / content 16 shows only 2 of its 4 slats over the content. Vertical slats split the full width. Tripwires: `test_slat_bounds_*`, `test_build_plan_letterboxed_slats_anchor_at_content`, `test_letterboxed_*`, `test_scaled_slats_snap_to_logical_rows`.
- **The reveal is `round(p * slat_size)` with `p = t / 0.95`, at real-pixel grain.** Depth is measured from each slat's leading edge, so `down`/`right` open from the low edge and `up`/`left` from the high edge. Tripwires: `test_mid_frame_down_reveals_top_of_each_slat`, `test_up_reveals_bottom_of_each_slat`, `test_right_and_left_use_columns`.
- **Default slats are looked up per orientation** (`DEFAULT_SLATS`, currently 8 for both; horizontal was 4 until the visual gate, where 4 read as about 2 bands on the bigsign). `slats=None` means "use this orientation's default", which is how `.alternating`/`.random` without `slats` give each direction its own default. Tripwire: `test_default_slats_by_orientation`.
- **Snapshot-only, snap idiom, refire rule** as interlock. Tripwires: `test_outgoing_not_drawn_live_after_snapshot`, `test_t0_always_starts_a_new_firing`, `TestRealCoreWidgets`, `TestPerfUniformity`.

## `flair.blink` animation invariants (`src/led_ticker_flair/flair/blink.py`)

- **Frame 0 is ON, and the cycle is quantized to engine ticks.** `period = max(2, round(period_ms / ENGINE_TICK_MS))`, `on = min(period - 1, max(1, round(period * duty)))`; `_is_on(frame)` is `frame % period < on`, so a visit always opens on visible text and a duty in (0, 1) always has at least one ON and one OFF tick. `count > 0` forces ON from frame `count * period` onward (it stops lit, never dark). Tripwires: `test_frame_zero_is_on`, `test_default_cycle`, `test_off_phase_blanks`, `test_count_stops_on`.
- **OFF is an EMPTY visible slice, not a draw skip.** `frame_for` returns `AnimationFrame(visible_text="")`, so the host's own layout (cursor advance, border, background) is untouched and the widget's end cursor does not change between phases; emoji and colored value tokens blank with the text. Tripwires: `test_empty_slice_with_emoji_and_token`, `test_message_end_cursor_unchanged`.
- **`frames_to_rest` feeds core's settle seam.** It returns the frames until the next ON phase (0 when already ON) so a hold that would end mid-OFF is extended and the transition leaves from visible text. THIS HOLDS FOR `message` WIDGETS ONLY: `gif`/`image` run `_play_with_text` (the `play()` path), which never reads `frames_to_transition_ready()`, so a blink (or typewriter) hold there can still end blank (core issue tracks it; do not promise otherwise in docs). `restart_on_visit = True` (each visit restarts at ON). Tripwire: `test_frames_to_rest_counts_to_next_on`.
- **WCAG 2.3.1 guard holds at the FASTEST engine cadence.** The animation counter advances once per scroll step (`scroll_step_ms` in ticker mode, `scroll_speed_ms` on image overlays, floor 20 ms), not per `ENGINE_TICK_MS`, so a 350 ms blink measured 7 Hz at 20 ms. Without `allow_fast`, `period_frames >= _MIN_SAFE_FRAMES (17)` (17 x `_FASTEST_TICK_MS` 20 = 340 ms, 2.94 Hz) is required, i.e. about `period_ms >= 850` (`round(period_ms / 50) >= 17`, so 826-849 also pass; the error and docs say "about 850"). The error names WCAG 2.3.1, the 20 ms cadence and `allow_fast`. Never relax the default or auto-enable it. `allow_fast` must be a real `bool` (tripwire `test_allow_fast_must_be_bool`). Arg validation rejects bool/non-numeric/nan/inf `period_ms` (via `_snow.validate_number`) and anything above 60000 ms (`test_period_ms_non_finite_or_huge_refused`), `duty` outside (0, 1), and non-int/negative `count`. Tripwires: `test_fast_rate_refused`, `test_min_safe_period_boundary`, `test_scroll_cadence_20ms_stays_under_3hz` (drives core's real scroll branch at `scroll_speed = 0.02`), `test_bad_args`.
- **OFF phase is capped at 20 frames (`_MAX_OFF_FRAMES`) regardless of `allow_fast`.** Core's settle seam extends a hold by at most `MAX_SETTLE_TICKS` (20); a longer OFF can't be waited out and the transition would start blank, so construction refuses `period - on > 20`. Tripwire: `test_off_phase_beyond_settle_cap_refused`.
- **First-draw cache cost (accepted).** Twinkle builds its caches lazily: the background's star list costs about 26 ms at 256x64 and the animation's row cache about 76 ms for a full-panel cold build on a Mac (likely 100-400 ms on a Pi). It is a one-time stall on the first visit of each instance, not per frame; do not add per-frame work to hide it.
- **`locks_resolution = False` on `Blink` and `Twinkle`.** Core's duck-typed opt-out of the per-visit token-resolution freeze: neither effect depends on the text content, so live `:id:` tokens keep updating mid-visit. Tripwire: `test_locks_resolution_false`. Twinkle's speed (like any frame-timed animation) scales with the scroll cadence on scrolling text; no cap change (it never goes fully dark, so it is not a WCAG flash).

## `flair.twinkle` animation invariants (`src/led_ticker_flair/flair/twinkle.py`, `_twinkle.py`)

- **Delivered through core's `AnimationFrame.pixel_gain` (core >= 4.33).** `frame_for` returns the full text plus a `gain(x, y) -> float` closure that core multiplies into each TEXT pixel only; borders and backgrounds are untouched. The floor is `led-ticker-core>=4.33` in `pyproject.toml` — do not lower it. Out-of-range coordinates (`x < 0` or `y < 0`) return 1.0.
- **Pure function of `(frame, x, y, seed)`; per-row cache.** Per-pixel hashing (`row_params`, the same `hash32` as the background) is done once per row in chunks of 64 columns and cached in `_rows`; the closure is list indexing plus a triangle wave. Re-rendering the same frame (transitions pause the host counter) gives the same gains regardless of which other frames were drawn in between. Tripwires: `test_pure_function_of_frame`, `test_gain_matches_level`, `test_gain_is_one_for_non_twinklers`, `test_row_params_agrees_with_is_twinkler_and_level` (`tests/test_flair_twinkle_math.py`).
- **Brightness floor and `speed` cap.** Gain never drops below `min_brightness` (`test_gain_floor`), and `speed` is capped at 2.0 (`test_speed_cap`) — faster would exceed the photosensitivity budget the blink guard enforces; `_twinkle` is also bounded at max speed (`test_level_bounds_at_max_speed`, `test_min_cycle_at_max_speed`). Validation is shared with the background via `validate_common` (bool/nan/out-of-range rejected; `test_bad_args`).
- **Granularity follows the font.** BDF text on a scaled sign twinkles per LOGICAL pixel (each block dims as a unit); hi-res text twinkles per REAL pixel. Tripwires: `test_bigsign_bdf_message_twinkles`, `test_bigsign_hires_message_twinkles`. Animated `SetImage` emoji are NOT gained (core only applies `pixel_gain` to text pixels and still sprites it draws pixel-by-pixel); do not promise they twinkle.
- **Twinkle is a HOLD effect.** Gain is panel-relative (`pixel_gain(x, y)` takes REAL panel coords), so on scrolling text the field is fixed to the panel and sparkles like noise — text-relative coordinates would need a core seam change. Documented in the README; do not "fix" it plugin-side. Twinkle/blink/typewriter/fisheye share ONE `animation` slot.
- **`restart_on_visit = False`, `frames_to_rest` is 0, `seed=None` draws one OS-entropy seed at construction** (the pattern differs per instance but is frame-pure afterwards). Perf: `test_perf_bigsign` bounds the bigsign draw cost — keep per-pixel work out of the closure.

## `flair.twinkle` BACKGROUND invariants (`src/led_ticker_flair/flair/twinkle_background.py`)

- **Same name as the animation, different registry.** `api.background("twinkle")` beside `api.animation("twinkle")`; core resolves each by slot. Subclass of `BackgroundEffectBase` (tripwire `test_is_background_effect`) with `frame_invariant = False`, `restart_on_visit = False`.
- **Stars are `is_twinkler` pixels of the REAL panel at `density` (default 0.03), painted at physical resolution.** `paint` unwraps with `unwrap_to_real` and never writes through the `ScaledCanvas` wrapper (tripwire `TestScaledCanvas::test_paints_only_on_real`); star count scales with real area (`test_star_count_scales_with_area`).
- **Pure function of `(frame_count, real dims)`; never black.** Each star paints `color * level` and a zero-after-scaling pixel is skipped, so the effect never erases a host's `bg_color` or an image beneath it. Tripwires: `test_pure_function_of_frame`, `test_unseeded_instance_is_still_frame_pure`, `test_never_paints_black`, `test_colors_scale_from_base`, `test_perf_bigsign`.

## `flair.snow` background invariants (`src/led_ticker_flair/flair/snow_background.py`, `_snow.py`)

- **One shared flake model (`_snow.py`) for the background AND the transition.** `flake_position(i, frame, ...)` is a pure function of `(i, frame, geometry, seed, speed, speed_variation, drift, wind, sprite_h)` — no `random`, no state; flake `i` falls at constant speed and wraps vertically, and each wrap (epoch) re-rolls its column and brightness. `flake_count(w, h, density)` scales with the REAL panel area (tripwire `test_count_by_geometry`). Do not fork the model; change it with both suites in mind.
- **Pure of `(frame_count, real dims)`, never black, physical resolution.** Tripwires: `test_pure_function_of_frame`, `test_unseeded_instance_is_frame_pure`, `test_flakes_fall`, `test_wrap_reenters_at_new_x`, `test_intensity_range`, `test_never_paints_black`, `TestScaledCanvas::test_paints_only_on_real`, `test_perf_bigsign`.
- **Emoji flakes are the 8x8 low-res sprite painted 1:1 on the real canvas — never block-expanded.** `flake = "dot"` (1 px), `"plus"` (5 px cross), `"flake"` (hand-drawn 5x5 asterisk, 9 px: center + 4 arm tips + 4 diagonals — `_FLAKE` in `_snow.py`; the built-in because `:snow:`'s 8x8 is a grey rain-cloud weather icon, not a snowflake; tripwires `test_builtin_flake_shape`, `test_builtin_flake_paints_never_black`), or an emoji slug whose 8x8 low-res form exists (`capture_sprite(slug, 1, None)`). On a bigsign the flake is therefore 8 physical pixels, not 32 (tripwire `test_emoji_flake_is_8px_on_bigsign`). Hires-only / pack-only slugs have no low-res form and are REFUSED at construction by `validate_flake` (`test_hires_only_slug_refused`, `test_unknown_slug_refused`) rather than silently falling back. Built-in flakes (`BUILTIN_FLAKES`: dot/plus/flake) shade by per-flake intensity (quantized to 16 steps); emoji flakes keep their sprite colors.
- **Numeric knobs are validated finite** (`validate_number` rejects bool, nan, inf): `density` in (0, 50] (`MAX_DENSITY`, `validate_density` — uncapped density 1000 cost ~121 ms/paint; tripwires `test_density_cap`, `test_transition_accepts_builtin_flake_and_caps_density`), `speed` in (0, 5], `speed_variation` in [0, 1), `drift >= 0`, `wind` any finite (tripwires `test_bad_args`, `test_non_finite_numbers_rejected`).

## `flair.snow` transition invariants (`src/led_ticker_flair/flair/snow.py`)

- **Snapshot-only, laser pattern.** Both widgets are snapshotted ONCE per firing into plugin-local physical-resolution `Raster`s (shared `_raster.py`) and stored as per-column sorted `(y, rgb)` lists; the outgoing widget is never drawn live after the snapshot. Tripwires: `TestSnapshots::test_outgoing_not_drawn_live_after_snapshot`, `test_refire_resnapshots`.
- **Refire rule: `t == 0.0 or t < _last_t` starts a new firing** (fresh snapshots); an equal non-zero `t` is NOT a refire. Tripwires: `test_t0_always_refires`, `test_equal_nonzero_t_is_not_a_refire`.
- **`seed=None` reseeds PER FIRING** (a fresh OS-entropy draw at every refire so each pass looks different); an explicit `seed` reproduces. Tripwires: `TestSeeding::test_unseeded_instance_differs_per_firing`, `test_explicit_seed_reproducible`.
- **Ragged per-column front.** `front(x, t) = (t / SNAP_THRESHOLD) * (h + J) - J + jit(x)` with `J = max(2, h // 4)`; incoming lit pixels above the front and outgoing lit pixels at/below it paint, so both sides coexist mid-transition (`test_front_monotone`, `test_front_mixes_both_sides_midway`, `test_t0_shows_only_outgoing`, `test_empty_outgoing`).
- **Flakes lead the front and fade to ZERO by the snap.** Flake count is scaled by `sin(pi * t / SNAP_THRESHOLD)` and driven by a pseudo-frame `int(t * FRAMES_PER_T)` at `FLAKE_SPEED`, so none remain at the snap. Tripwire: `test_flakes_peak_midway_and_absent_at_ends`.
- **Snap idiom + `scale_switch_at = 1.0`.** At `t >= SNAP_THRESHOLD`: `snap_reset(canvas, incoming_bg_color)` then `incoming.draw(canvas, cursor_pos=0)` (`test_snap_shows_only_incoming`, `test_no_outgoing_pixels_after_snap`, `test_bordered_incoming_no_flash`). Because the scale switch is deferred to the snap, sections with different `bg_color` POP at the snap rather than following the front — the same accepted limitation as laser/fairy.
- **Physical resolution; `unwrap_to_real` every call** (`TestScaled::test_scaled_physical_resolution`). `mode = "build"` is reserved and refused (`test_build_mode_refused`); unknown modes, bad flakes, colors, densities and non-finite numbers raise (`test_unknown_mode`, `test_bad_flake`, `test_bad_color_and_density`, `test_non_finite_rejected`). Perf: `TestPerf::test_perf_bigsign`.
