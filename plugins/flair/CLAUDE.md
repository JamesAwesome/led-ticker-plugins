# CLAUDE.md — led-ticker-flair

One wheel, five plugin namespaces: four sprite-trail families (`nyancat`, `pokeball`, `pacman`, `sailor_moon`) plus `flair` (the wheel's own name, for text effects). Each sprite family lives under `src/led_ticker_flair/<family>/`, registered in `src/led_ticker_flair/<family>/__init__.py` as `forward` / `reverse` / `alternating`. The `flair` namespace registers text effects: two animations (`flair.propeller`, `flair.fisheye`), one transition (`flair.spinout`), and one widget (`flair.lottery`).

## Invariants

- **One wheel / five entry points** — `pyproject.toml` declares all five `led_ticker.plugins` entry points (`nyancat`, `pokeball`, `pacman`, `sailor_moon`, `flair`). The entry-point NAME is the plugin namespace; transition type strings are `<namespace>.<variant>`, animation type strings are `<namespace>.<name>`, widget type strings are `<namespace>.<name>`.
- **`flair` namespace naming exception** — unlike the four sprite families, the `flair` namespace is named after the wheel itself, not a sprite character. This is an intentional exception to the namespace-per-sprite-family pattern. It registers text effects — the `flair.propeller` + `flair.fisheye` animations, the `flair.spinout` transition, and the `flair.lottery` widget — and has no `sprites/` directory.
- **Sprites load via `Path(__file__).parent / "sprites"`** — sprites live beside the family module file (e.g. `src/led_ticker_flair/nyancat/sprites/nyancat.webp`). Moving a family submodule without moving its `sprites/` directory breaks sprite loading. The `flair` submodule has no sprites and is not subject to this invariant.
- **Imports only from `led_ticker.plugin`** — enforced per-family by `tests/test_import_purity.py`.
- **No `from __future__ import annotations`** (PEP 649 / Python 3.14 rule).
- Dep: `led-ticker` only.
- Lint/test from the monorepo root: `make lint` / `uv run pytest plugins/flair`. CI is the root path-filtered matrix.

  resolve against an editable pre-release core (hatch-vcs reports e.g.
  `4.2.2.devN`); install with `uv pip install --no-deps -e plugins/flair` and

  dx_logical=...)` translation seam (see the blit-geometry bullet below); the

  monorepo's own `pyproject.toml`/`uv.lock` carry an uncommitted, worktree-local
  `[tool.uv.sources]` override pointing `led-ticker-core` at the core seam
  worktree. Never commit that override.

## `flair.lottery` widget invariants (`src/led_ticker_flair/flair/lottery.py`)

- **Choreography: rack-fill, not left-to-right.** The first ball to enter rolls to the RIGHTMOST slot; the next stops one slot short; and so on — a rack fills, no ball ever crosses (rolls through) an already-settled one. Reveal order is therefore right-to-left (the last config word lands first), but word index always equals slot index, so the FINAL display still reads the config's `words` left-to-right unchanged. `roll_order_for_slot(slot_index, n)` is the (self-inverse) mapping between a slot's index and its temporal roll order — `draw()`'s per-tick loop walks slots in REVERSED (rightmost-first) order and feeds `ball_phase` the roll order, not the slot index, as its tick-window argument. `ball_phase` itself is pure per-ball math and stays agnostic to which slot owns which window — only this mapping layer changed. The correctness argument is geometric, not just empirical: because slot stride (`diameter + _GAP_PX`) exceeds the ball diameter, and a rolling ball's `cx` never exceeds its own target slot center, a still-rolling ball's footprint can never reach the footprint of any slot further right (i.e. any already-settled one). Tripwire: `TestRackFillChoreography` in `tests/test_flair_lottery.py`, specifically `test_no_ball_ever_crosses_a_settled_one` (snapshots every settled ball's face region every tick and asserts it's byte-identical while any other ball is still rolling — this is the test that pins the regression the fix addresses; it fails hard under the old left-to-right entry order).
- **Two-surface design, one repaint+snapshot per settle — NEVER per tick.** Each ball owns its own construct-once `RotationSurface` (built by `_ensure_built`, painted with its face ONE time at its slot position, then `snapshot()`'d) plus one shared `_rest_surface` composite that already-settled balls get folded into. Every tick, `draw()` does exactly two kinds of surface work: (1) a flat identity `_rest_surface.blit(canvas, 0.0, 0.0)` for all already-settled balls (cheap, O(1) regardless of `n`), and (2) a single rotate+translate `blit()` for the one ball currently rolling. A ball transitions from its own surface to the rest composite via exactly one `paint_face` + `snapshot()` call at the tick it settles — never repainted again after that. This is the same perf contract as `flair.propeller`/`flair.fisheye`: painting (SetPixel-heavy, expensive) happens O(1) times per ball; blitting (cheap) happens every tick. Do not "simplify" this into repainting every ball's face every tick — that reintroduces the O(n) per-tick SetPixel cost the two-surface design exists to avoid.
- **Blit geometry — pivot vs. translation (the core >=4.10 seam).** `RotationSurface.blit(canvas, angle_deg, cx_logical, dx_logical=...)` takes the pivot (`cx_logical`) and the translation (`dx_logical`) as independent parameters. Lottery passes the ball's own painted SLOT center as the pivot — this makes the face spin about ITSELF (tumbling in place) rather than about the panel origin — and `dx_logical = current_cx - slot_cx` as the translation, which slides that spinning face sideways to wherever it currently is along the roll. Verified against core's `rotate.rotate_blit` forward map `dst = R(src - c) + c + t`: pivot and translation are independent terms, so this composes cleanly (a word can spin AND slide in the same blit). This translation parameter (`dx_logical`) did not exist before the Phase-0 core seam (PR #367) — it's why this widget bumped the core floor to `>=4.10`. Don't confuse pivot and translation: swapping them (e.g. pivoting on the current rolling position instead of the slot) makes the ball orbit the panel instead of tumbling in place.
- **Roll timeline reads `_frame_count` directly, NOT `frame_for("roll")`.** `FrameAwareBase._EFFECT_ATTRS` is a fixed, enumerated set of named per-effect counters (`"border"` is a member; `"roll"` is not). Calling `self.frame_for("roll")` on an unlisted name would silently alias `self._frame_count` rather than raising — a footgun-shaped trap for a future refactor that assumes every named string works. `ball_phase(frame, ...)` in `draw()` is deliberately called with `self._frame_count` verbatim. If a future change adds `"roll"` to `_EFFECT_ATTRS` upstream in core, this widget's counter semantics (resets to 0 every visit via `reset_frame`, which is also when the two surfaces get dropped/rebuilt = the re-roll) must stay in lockstep with that reset — don't switch to `frame_for("roll")` without re-verifying the reset timing matches.
- **Unit convention: layout is physical, blit args are logical.** `layout()`, `ball_phase()`, and the widget's `_diameter_px`/`_slot_centers_px`/`_r_px` are all REAL (physical) pixels — the balls paint directly to the real canvas via `paint_hires` (bypassing `ScaledCanvas`'s block expansion), same as hi-res emoji, so their geometry must be computed in the same space the panel itself is measured in. But `RotationSurface.blit()`'s `cx_logical`/`dx_logical` arguments are LOGICAL — the widget's own drawing space, matching `paint_face`'s `cx_logical`/`cy_logical` params. `draw()` converts at the boundary: `cx_logical = cx_real / canvas.scale` before computing `dx_logical = cx_logical - slot_cx`. Getting this backwards (passing a physical-pixel value where `blit` expects logical, or vice versa) produces a ball that rolls at the wrong speed or position without raising — verify unit provenance at every call site that touches both spaces, not just the ones that "look wrong" on inspection.
- **`y_offset` renders the CURRENT roll frame shifted, via `dy_logical` — not an all-settled substitute (fixed; was the MAJOR finding from the lottery review).** `y_offset` is LOGICAL units, the same unit `RotationSurface.blit`'s `dy_logical` keyword takes (core `>=4.10` — see the co-dev note above; `dy_logical` landed as part of the same seam as `dx_logical`), so `draw()` forwards `dy_logical=float(y_offset)` to every `blit()` call (the rest-surface identity blit AND the per-tick rolling/settling blits) instead of branching to a separate direct-paint path. There is no longer a `y_offset != 0` special case: the SAME two-surface rendering runs regardless of `y_offset`, just translated. Consequences (correct, by design): an incoming push transition resets the widget first (frame 0, `RotationSurface`s dropped) — so the push slides in whatever frame 0 actually looks like (empty / a ball barely leaving the left edge), and the roll plays out AFTER the push completes, preserving the reveal. An outgoing mid-roll push shows the exact mid-roll state (some balls settled, one rolling, others off-canvas), shifted — no more unrolled balls popping into existence. This is safe specifically because `run_transition` calls `pause_frame()` around the whole transition, so repeatedly drawing "the current frame" during a multi-tick transition composite is a still frame, not a redraw of an advancing roll. Tripwire: `TestLotteryWidget.test_y_offset_renders_current_frame_shifted` (mid-roll shift-consistency) and `test_y_offset_incoming_push_does_not_reveal_finished_row` (regression probe for the original bug) in `tests/test_flair_lottery.py`.
- **Unfittable-word warn latch (`_warned_words`).** `paint_face` logs one WARNING per unfittable word (a word whose largest font size at the ball's diameter still doesn't fit — `auto_font_size` returns 0). Without a latch, every visit's `_ensure_built` rebuild (which happens on every `reset_frame`, i.e. every re-roll) would re-log the same word forever. `_warned_words` is a `set[str]` that persists ACROSS `reset_frame` calls (deliberately NOT reset alongside `_surfaces`/`_rest_surface`/`_built_for`, which DO get dropped every visit) — it's keyed on the word/font/diameter combination being persistently unfittable, not on a specific surface generation. `_ensure_built` passes `warn=not fits and word not in self._warned_words` per word and adds to the set right after checking; the settle-time `paint_face` call passes `warn_unfittable=False` unconditionally (the one warning already fired during `_ensure_built`, if it was going to).
